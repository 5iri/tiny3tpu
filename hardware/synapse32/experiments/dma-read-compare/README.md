# DMA burst-completion comparison

With carry connectivity restored in the diagnostic graph, DMA burst completion
is part of the long system paths. The read engine computes a remaining byte
count by subtraction and then tests whether the result is nonzero. A direct
comparison of the two same-width unsigned counts makes exactly the same
decision, including modular underflow, while removing the subtraction from
the descriptor-ready decision cone. The stored remaining count still updates
as before.

The original `third_party/verilog-axi/rtl/axi_dma_rd.v` is unchanged. The opt-in
`--dma-read-compare` flag supplies a generated copy for unit simulation, full
SoC simulation and board synthesis. The driver verifies proof/source hashes,
exact generated bytes and source selection. No stage or bus cycle is added.

`build-dma-read-compare/results.json` proves the changed decision without any
state, alignment or handshake assumptions, at widths 1, 2, 8, 12, 16, 32 and
64. The current engine uses 16 bits. Every other byte of the RTL is unchanged.
The open DMA/TPU unit test passes 27 cases, 3,693 read beats, 3,685 write beats
and 16,345 cycles. Smoke and 45-shape PROFILE, METRICS and DMA records exactly
match the retained selector baseline:

| Workload | Instructions | Enabled CPU cycles | System cycles |
|---|---:|---:|---:|
| Smoke | 106,588 | 142,895 | 789,205 |
| 45 shapes | 1,659,843 | 2,084,686 | 11,544,608 |

Synthesis passes: 661 versus 662 CARRY4s; FDRE/FDCE, DSP and BRAM counts are
unchanged. The firmware is unchanged.

**Timing remains diagnostic.** The backend has missing carry timing data and
other primitive/clock limitations. In the expanded graph, with those unknown
values kept symbolic, the seed-8 comparison is:

| Unknown carry arc / PCOUT clock delay | Baseline worst interval | Candidate worst interval |
|---|---:|---:|
| 0 ns / 0 ns | 17.320 ns | 15.520 ns |
| 0 ns / 1 ns | 17.320 ns | 15.520 ns |
| 0.1 ns / 0 ns | 17.910 ns | 15.720 ns |

For the zero-substitution case, the candidate's system-to-system maximum is
15.184 ns versus 17.320 ns, but CPU-to-system worsens from 13.523 to 15.520 ns.
The candidate's critical endpoints are now UART RX FIFO count and CPU store
data. Seed 4 is worse (20.137 ns worst at zero substitutions); no physical
Fmax improvement or 100 MHz closure is claimed. Seed 8 is a promising
experiment under the expanded model, not a promoted board default.

Evidence:
`build-ddr-control8-timing-sensitivity-constant-aware/manifest.json`,
`build-ddr-read-compare8-timing-sensitivity/manifest.json`,
`build-ddr-read-compare4-timing-sensitivity/manifest.json`.

The old incomplete backend prints 89.49/107.12 MHz system/CPU for candidate
seed 8 and 81.12/103.18 MHz for seed 4. Those figures exclude carry paths and
must not be used to rank whole-SoC timing. Raw reports, all clock targets,
crossings and strict DDR warnings remain preserved in
`build-ddr-seeds-read-compare-graph`.

```sh
python3 hardware/synapse32/experiments/dma/run.py system --out build-dma-compare-new \
  --cpu-overlay-dir build-ddr-divider-payload/overlay --system-mul \
  --bus-payload --uart-control --dram-command-buffer --dram-write-buffer \
  --packed-rows --firmware-opt=-O3 --tpu-counters --csr-read-direct \
  --dram-parallel-chooser --dma-read-compare
```

Use the same flags for synthesis after current validation. Timing coverage
limitations are detailed in [core timing](../core-timing/README.md).
