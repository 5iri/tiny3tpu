# Direct DMA write last-cycle flags

The previous best expanded graph (atomic word input + UART and boot decodes,
seed 4) ends at `axi_dma_wr_inst.output_last_cycle_reg`, at 13.961 ns with zero
symbolic carry and cascade delays. Its path traverses burst sizing and the
initial beat-count decrement before testing for zero. Trace:
`build-ddr-atomic-boot4-timing-sensitivity/dma-write-traces.json`.

This candidate leaves every count update in place and changes three flag
assignments. For the current aligned 32-bit engine (16-bit length, two-bit
byte offset, 15-bit cycle count), an initial last beat is exactly a transfer
length of 1..4 bytes. Zero length retains the original underflow behavior.
Other initial parameter profiles retain the original expression. At both
subsequent decrement sites, `(count - 1) == 0` after same-width storage becomes
`count == 1`, including modular wraparound.

No register, pipeline stage, AXI beat, response rule or firmware change is
introduced. The third-party source is unchanged; `--dma-write-last` selects
a generated copy explicitly for unit simulation, SoC simulation and synthesis.
The driver verifies proof hashes and exact generated bytes before selection;
synthesis requires the selected source to match passing SoC validation.

`build-dma-write-last/results.json` proves the initial condition for all 16-bit
transfer counts and the decrement condition for all counter values at widths
1, 2, 8, 15, 16, 32 and 64. No nonzero-length or reachable-state assumption is
used. The generator verifies that reversing the replacements recovers the
entire original module.

Validation passes:

- DMA/TPU unit: 27 cases, 3,693 read beats, 3,685 write beats, 16,345 cycles.
- Smoke: 106,588 instructions, 142,895 enabled CPU edges, 789,205 system cycles.
- 45 shapes: 1,659,843 instructions, 2,084,686 enabled CPU edges, 11,544,608
  system cycles. Complete PROFILE, METRICS and DMA fields match the preceding
  atomic/boot candidate exactly, including IPC and per-instruction records.

Evidence: `build-unit-dma-write-last/unit.log`,
`build-dma-write-last/throughput-comparison.json`, and
`build-ddr-dma-write-last/board`.

Synthesis uses 654 CARRY4s and 6,508 LUT6s versus the preceding candidate's
653 and 6,436. Register, DSP and BRAM counts, firmware and XDC bytes are
unchanged. The count datapath remains necessary, so removing it from the flag
does not necessarily reduce total logic.

These are the largest expanded diagnostic intervals. The small improvement
in the zero-substitution case does not persist in the carry sensitivity case;
this is not a clear replacement for the preceding candidate. Evidence:
`build-ddr-write-last4-timing-sensitivity/manifest.json` and
`build-ddr-write-last8-timing-sensitivity/manifest.json`. The next probe derives
the initial flag [directly from length and page position](../dma-write-short/README.md).

```sh
python3 hardware/synapse32/experiments/dma-write-last/prove.py --out build-write-last-new

python3 hardware/synapse32/experiments/dma/run.py system \
  --out build-dma-write-last-new --cpu-overlay-dir build-atomic-word-v2/overlay \
  --system-mul --bus-payload --uart-control --dram-command-buffer \
  --dram-write-buffer --packed-rows --firmware-opt=-O3 --tpu-counters \
  --csr-read-direct --dram-parallel-chooser --dma-read-compare \
  --uart-address-decode --boot-address-decode --dma-write-last
```

The driver uses `build-dma-write-last/results.json` as its proof evidence.
No board defaults are promoted. [Timing-model gaps](../core-timing/README.md)
still prevent physical Fmax verification; symbolic-delay graphs are diagnostic.
